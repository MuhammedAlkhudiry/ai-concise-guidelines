# Product Health Source Adapters

- Sentry: use $sentry-cli and its current help for issues, events, traces, performance, setup, and safe cleanup. Use $sentry-sdk-upgrade for JavaScript SDK migrations. Fetch full issue details and representative events before reporting or resolving an issue; do not mutate releases, alerts, projects, or active issues.
- Laravel/Horizon/jobs: discover the project's queue and scheduler surfaces from code and config. Use Sentry first, then the project's documented read-only Artisan, SSH, or Forge route. Measure backlog, age, retries, failures, and successful execution from live state.
- Server: use project deployment docs plus current Forge CLI help or SSH tooling. Inspect only the services and capacity signals the deployment actually uses; do not mutate services.
- Database: use $service-access for provider access, then the provider CLI/API help and live schema for health, capacity, backup, maintenance, performance, and read-only integrity evidence. Do not report credentials.
- Redis: discover its cache, session, queue, or Horizon role from project config. Use current Redis command help and read-only server telemetry for health, memory, clients, latency, and eviction evidence.
- PostHog: use $posthog-cli and the configured PostHog skills for analytics, metric investigations, and SDK health. Stay on product analytics unless the repo or user expands scope.
- AI/agentic features: detect assistant, chat, agent, conversation, run, step, usage, tool-call, credit, and proposal models/events. Audit adoption, repeat use, run success/failure, latency, tool/action distribution, unresolved sessions, write/proposal follow-through, safety blocks, credit/cost pressure, and friction from real user transcripts or structured events.
- Typesense/search: discover the active search provider and integration from project manifests and config. Check Sentry first, then use the provider's current read-only health/metrics API and live collection state for availability and indexing-drift evidence.
